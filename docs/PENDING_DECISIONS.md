# Pending Decisions

- Package alias shape for the final NAPI publishing flow still needs to be finalized after the Rust surface stabilizes. It must cover Vue 2.6 and Vue 2.7 `vue-template-compiler`, Vue 2.7 `vue/compiler-sfc`, and Vue 3 `@vue/compiler-*` entries without changing official test imports.
- NAPI-backed official package-name source conformance is now executable and passing for all seven suites, but coverage classification is intentionally different from generated-alias coverage. Current NAPI reports include mixed-heavy paths for Vue 2 compiler suites, Vue 3 compiler-core internal source imports, and Vue 3 compiler-sfc source helpers, while generated-alias reports are the current Rust-backed completion evidence for those compiler semantics.
- `target/compat/rust-alias/<version-line>` remains the generated probe root for compatibility summaries and Rust-backed coverage accounting. `target/compat/napi-alias/<version-line>` is the version-isolated NAPI public contract/source probe root; any future NAPI source-conformance migration must preserve official package names/subpaths and must not reclassify mixed source-runner adapter execution as Rust-backed.
- Option matrix rows are now executable with all current generated and NAPI targets passing. Future callback/plugin-style option rows must either serialize a Rust-observable contract or be recorded as JavaScript API-boundary behavior; they should not be deleted or counted as Rust compiler semantics.
- Vue 3 compiler-core conformance reporting now has suite-level, file-level, and assertion-group execution-source classification. The remaining refinement question is whether future reports should split even further by individual test or API entry; the current mixed groups are caller-provided JavaScript callback/context boundaries.
- The broad Vue 3 compiler-core alias-runtime replacement decision is largely closed for generated-alias completion by Rust-backed bridge suites and public compile/codegen coverage. Keep any remaining JavaScript alias code documented as import/API/test-runner/AST hydration support or explicit JS callback-boundary materialization, not compiler semantics.
- Release dry-run has an objective artifact-consuming gate in `cargo xtask verify-release-dry-run --native-artifacts-dir <dir>`. The gate can prove native platform npm tarball contents when release-built `vuec_napi.node` inputs are available as `<platform>/vuec_napi.node`, `<platform>.node`, or the downloaded GitHub artifact wrapper layout such as `native-Linux-X64/linux-x64-gnu/vuec_napi.node`; first-time crates.io dry-runs for crates with internal path dependencies still require dependency crates to be published to the registry first.
- Release install smoke has an objective current-host gate in `cargo xtask verify-release-install-smoke --current-platform-only`. The CI workflow runs this on Windows/Linux/macOS and feeds the resulting native artifacts into release dry-run, but full M20 install-smoke completion still requires matching host runs for every required OS/arch/libc platform variant.
